# Token Saving 随用量增长的预期分析

**日期**: 2026-05-25  
**背景**: Task29 实验显示 confidence-based context compaction 在模拟环境下节省约 4.7-5.3% 的 context token。本文分析在真实生产环境中，随着用户交互量增长，该比例的预期增长路径及天花板。

---

## 1. 论文中 ~5% Saving 被限制的原因

```
当前实验条件：
  - 交互次数：8 epochs × 596 queries ≈ 4800 次
  - 高置信比例：~30-33% (linucb_primary_rate)
  - 压缩策略：高置信 k=8, 其余 k=10（仅省 2 个 chunk）
  - 理论最大单查询 saving：2/10 = 20%

实际 saving ≈ 高置信比例 × 单查询 saving
            ≈ 33% × 20% × (avg_token_per_chunk 调整)
            ≈ 5-6%（与实验吻合）
```

瓶颈不在方法本身，而在交互量不足 → confidence 不够高 → 高置信比例低 → 被压缩的查询少。

---

## 2. 生产环境中推动 Token Saving 增长的因素

| 因素 | 论文实验 | 生产环境（随时间） | 对 saving 的影响 |
|------|---------|------------------|-----------------|
| 累计交互次数 | ~4800 | 数万-数十万 | confidence 更准确、更多查询通过门槛 |
| 高置信查询比例 | ~30% | 预期 → 60-80% | 更大比例的查询被压缩 |
| 重复 query 模式 | 596 unique queries | 企业场景 80/20 分布 | 热门 pattern 极高置信，可激进压缩 |
| 压缩档位 | 仅 k=8 一档 | 可分 k=8/k=5/k=3 多档 | 超高置信查询可压缩更多 |
| 个性化 | 无 | 按用户/角色学习 | 熟悉用户可更激进 |
| 阈值自适应 | 固定 0.65/0.35 | 监控质量后动态调低 | 更多查询通过门槛 |

## 4. 关键驱动力：企业 Query 的 Zipf 分布

企业 RAG 场景中，query 分布高度不均匀（80% 流量集中在 20% 的 pattern）：

```
热门 query（如"XXX产品怎么用"、"出差报销流程"）：
  → 历史交互 500+ 次 → LinUCB 极高置信
  → 可压缩到 k=3（70% token saving）

中频 query（如特定型号技术参数查询）：
  → 历史交互 50-100 次 → 高置信
  → 压缩到 k=5-6（40-50% token saving）

长尾 query（首次出现的新问题）：
  → 无历史 → 低置信 → fallback k=10
  → 0% token saving

加权平均示例：
  40% 热门(saving 60%) + 35% 中频(saving 35%) + 25% 长尾(saving 0%)
  → 整体 saving ≈ 40%×60% + 35%×35% + 25%×0% = 24% + 12.25% = ~36%
```

实际会比这低一些（保守阈值、质量底线等），预期稳态 **25-35%**。

---

## 5. 个性化放大效应

不同用户的 query 分布不同：

| 用户类型 | 特征 | LinUCB 学到的策略 | 个人 saving |
|---------|------|-----------------|-----------|
| 高频专业用户 | 反复问同领域技术问题 | 极高 cluster 置信 | ~40-50% |
| 管理层用户 | 偶尔查规章制度 | 中等置信 | ~15-20% |
| 新用户 | query 模式未知 | 低置信，多 fallback | ~5% |

系统整体 saving = 各用户 saving 按 query 量加权。高频用户贡献的交互量大，拉高整体。

---

## 6. 天花板分析

Token saving 不会无限增长，受以下因素制约：

| 限制 | 原因 | 天花板影响 |
|------|------|-----------|
| 最少 context 需求 | 即使极高置信也需 1-3 chunk 保证回答有据 | 单查询最多省 70-80% |
| 长尾 query | 始终有 ~20-30% 的查询无足够历史 | 无法对这部分压缩 |
| 分布漂移 | 新文档/新话题加入 → confidence 暂时下降 | 周期性回落 |
| 质量底线 | 过度压缩 → hallucination 增加 | 必须保守 |
| 新用户占比 | 新用户无历史 → 无法个性化 | 拖低整体 |

**综合天花板估计**：
- 保守（质量优先）：**25-35%**
- 中等（可接受轻微质量下降）：**35-45%**
- 激进（接受部分长尾质量损失）：**45-55%**

---

## 7. 与论文的关系

论文报告的 ~5% 是**下界**，不是能力上限。论文中可以这样表述：

> "The current 4.7-5.3% token saving is measured under a conservative policy
> with limited interaction history (~4800 rounds). In deployment scenarios with
> higher query volumes, repeated patterns, and personalized confidence, the
> achievable saving is expected to grow substantially. The relationship between
> interaction volume and token reduction is a direction for future production
> evaluation."

这为后续在 jq_kg_base / jq_legal_base 中的工程验证预留了接口。

## 8. 论文之外的工程价值计算

假设企业 RAG 系统日均 10,000 次查询，平均 context 1500 tokens/次：

| 阶段 | Token saving | 日省 tokens | 月省 tokens | 按 GPT-4 输入价格折算/月 |
|------|-------------|------------|------------|------------------------|
| 上线初期 (5%) | 5% | 750k | 22.5M | ~$67 |
| 稳定期 (20%) | 20% | 3M | 90M | ~$270 |
| 成熟期 (30%) | 30% | 4.5M | 135M | ~$405 |

对于大规模部署（日均 100k+ 查询），这些数字放大 10 倍。

## 9. 总结

| 问题 | 回答 |
|------|------|
| 论文 5% saving 是上限吗？ | 否，是交互量有限条件下的下界 |
| 生产中能增长吗？ | 是，随交互量、重复模式、个性化持续增长 |
| 增长曲线是什么形状？ | 前期快（热门 pattern 快速学到），后期趋缓（长尾+天花板） |
| 天花板在哪？ | 保守 25-35%，中等 35-45% |
| 核心驱动力？ | Zipf query 分布 + confidence 累积 + 多档压缩 |
